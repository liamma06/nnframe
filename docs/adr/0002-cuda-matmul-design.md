# Standalone device-pointer CUDA matmul, kept separate from Tensor and gated behind an optional CMake toggle

**Status**: accepted

M9 adds a CUDA backend, starting with a single op: matmul, the same op M8 vectorized with AVX2. Rather than wiring a `Device` concept into `Tensor` on day one, the CUDA kernel is written and correctness-checked in complete isolation — `src/cuda/matmul_cuda.cu` / `include/cuda/matmul_cuda.cuh`, with no changes to `Tensor` or any existing file — mirroring how M8 actually went: prove the kernel correct and measured against a trusted CPU reference (`matmul_scalar`) before any framework integration. `Tensor::matmul()` continues to call `matmul_avx2` unchanged; CPU (scalar) and SIMD (AVX2) remain fully intact as separate, existing paths — CUDA is a third option added alongside them, not a replacement for either, and M9 does not decide how (or whether) `Tensor` picks a backend. That is deliberately left to a future milestone, once the kernel itself is proven.

The CUDA toolkit is not assumed to be present on every machine this repo is built on (the author's laptop is CPU-only; the desktop has an NVIDIA GPU). `CMakeLists.txt` gates all CUDA-related lines — `enable_language(CUDA)`, `CMAKE_CUDA_ARCHITECTURES`, and the new CUDA targets — behind `option(NNFRAME_WITH_CUDA "Build CUDA targets" ON)`, defaulting on. A GPU-less machine configures with `-DNNFRAME_WITH_CUDA=OFF` and still builds every CPU/SIMD target (`test_m1`–`test_m7`, `xor`, `char_lm`, `matmul_benchmark`, etc.) untouched.

`CMAKE_CUDA_ARCHITECTURES` is set to `native` rather than a hardcoded compute-capability number (e.g. `75` for the desktop's GTX 1660, Turing). CMake 4.4.2 (the installed version) auto-detects whatever GPU is present at configure time. Since this project already only compiles CUDA code on machines that have a GPU (`NNFRAME_WITH_CUDA` handles the GPU-less case), `native` and a hardcoded `75` produce an identical result on the author's own hardware — the deciding factor is portability if anyone else ever clones and builds this on a different NVIDIA GPU, where a hardcoded value would silently target the wrong architecture.

The first (and so far only) kernel is a naive global-memory matmul — no shared-memory tiling, no warm-up/toy kernel (e.g. vector-add) written first. A trivial warm-up kernel was considered, since M9's stated goal is to go slow and prioritize understanding the GPU memory model over speed of implementation, but was dropped: the only new concept naive matmul adds over a toy kernel is 2D thread indexing (`row`/`col` from `blockIdx`/`blockDim`/`threadIdx`), and the naive matmul is kept afterward and benchmarked, unlike a throwaway warm-up. Every CUDA API call (`cudaMalloc`, `cudaMemcpy`, kernel launch, `cudaFree`) is wrapped from the first line of code in a `CUDA_CHECK` macro that checks the returned `cudaError_t` and aborts with file/line on failure — CUDA fails silently by default (a bad launch just doesn't run, no exception), and this is a one-time, ~10-line cost against real debugging pain, especially on a first kernel where indexing, memory transfer, and launch configuration are all new at once.

The host-facing function takes **device pointers**, not host pointers — the caller (test/benchmark code) is responsible for `cudaMalloc`/`cudaMemcpy` upload/download around the kernel launch, rather than the matmul function silently doing a full host-to-device-to-host round trip on every call. This was chosen deliberately over mirroring `matmul_avx2`'s host-pointer signature: a host-pointer wrapper would pay full PCIe transfer cost on every single call, which is not how real GPU-resident workloads are structured (data uploaded once, reused across many kernel launches) and would hide the actual memory-model lesson M9 is about. Thread blocks are launched as `16x16` (256 threads/block) — the standard starting point for a naive kernel, warp-aligned (8 full warps/block), and not a meaningfully performance-sensitive choice at the naive (non-tiled) stage; block-size tuning becomes a real decision once shared-memory tiling is added later.

Correctness and performance measurement are kept in separate files, unlike M8's `matmul_benchmark.cpp`, which combined a printed PASS/FAIL correctness check with timing in one file — a real gap against this project's "one test file per milestone, all green" rule, since a printed FAIL doesn't fail the test suite the way a doctest `CHECK()` does. `tests/test_m9_cuda.cpp` (doctest, gated behind `NNFRAME_WITH_CUDA`) checks CUDA output against `matmul_scalar` at `1e-3f` tolerance — the same tolerance M8 used for scalar-vs-AVX2, since the root cause (floating-point accumulation order differing across implementations) is the same regardless of backend — using small matrix sizes (64x64x64, plus a non-multiple-of-16 size to exercise the kernel's out-of-bounds thread guard) so the suite stays fast. `examples/matmul_cuda_benchmark.cpp` handles timing only, at a realistic 512x512x512 size, and reports kernel-only compute time (wrapping just the launch plus `cudaDeviceSynchronize()`) separately from full round-trip time (alloc + upload + compute + download + free) — collapsing these into one number would hide whether GPU wall-clock time is dominated by compute or by data transfer, which is itself one of the central lessons of this milestone.
