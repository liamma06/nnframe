# Device-on-Tensor abstraction: matmul-only, forward-only, single-buffer, exceptions for device errors

**Status**: accepted

M9 proved a standalone CUDA matmul kernel correct in isolation, with no changes to `Tensor` (ADR-0002). This milestone wires that kernel into `Tensor` itself via a `Device` concept, so `tensor.matmul(other)` can dispatch to CPU (`matmul_avx2`/`matmul_scalar`) or GPU (`matmul_cuda`) depending on where the tensor lives, instead of requiring hand-written `cudaMalloc`/`cudaMemcpy` at every call site.

Scope is deliberately narrow on two axes. First, only `matmul` gets a `Device`-aware dispatch path — every other op (`ReLU`, `+`, `reshape`, softmax, etc.) has no CUDA implementation yet. Real end-to-end speedup requires a whole forward pass to stay GPU-resident (one upload, many ops, one download); porting `matmul` alone while everything else stays CPU-only would mean per-op transfers whose cost (measured in the M9 benchmark at ~94% of wall-clock time for a single matmul) would likely make a full pass *slower*, not faster. Porting the ops needed for a full forward pass (GELU, softmax, LayerNorm, masking) is the explicit next milestone, not deferred indefinitely. Second, this milestone is forward-only — no `matmul_grad_cuda`, and autograd's computation graph does not yet track device per-node. GPU-backed backward pass is its own milestone-sized chunk of kernel work (two gradient kernels, `dL/dA` and `dL/dB`, mirroring the existing `matmul_grad_avx2`/`matmul_grad_scalar` split) and is the milestone immediately following this one.

`Device` is a two-value enum, `CPU` and `CUDA` — not finer-grained (e.g. separate `CPU_SCALAR`/`CPU_AVX2` values). AVX2-vs-scalar selection remains an internal implementation detail of the CPU path, exactly as it's been since M8: `matmul()` already picks AVX2 when beneficial and falls back to scalar, with no user-visible choice. `Device` describes *where data physically lives* (host RAM vs GPU VRAM), not *how* compute happens within a location.

A `Tensor` is resident on exactly one device at a time — no dual-residency/caching between CPU and GPU. `.to(Device)` returns a new `Tensor` on the target device rather than mutating the receiver in place, matching how `reshape`/`permute` already build new tensors rather than mutating. Every new `Tensor` starts on `CPU` by default, so every existing constructor call site across M1-M9 remains correct with zero changes. Dual-residency was considered and rejected: it requires cache-invalidation logic (which copy is stale after a write?) that current and near-term (M10 continuous batching/paged KV cache) usage patterns don't need — both are shaped as "move once, operate many times, move back once," which single-buffer directly supports.

Internally, `Tensor` keeps its existing `std::vector<scalar_t>` for CPU data untouched, and adds a separate raw device-pointer field used only when `device() == CUDA`. An alternative — dropping `std::vector` entirely in favor of one raw pointer field manually managed for both CPU and GPU — was rejected as a large, risk-only rewrite of CPU memory handling that's been correct since M1, purely to make the two cases symmetric. Because a GPU-resident tensor's device pointer is `cudaMalloc`-owned, `Tensor`'s copy constructor and copy assignment are deleted whenever GPU residency is possible — the compiler's default member-wise copy would duplicate the pointer, and both copies' destructors would then `cudaFree` the same address (double-free). The codebase already passes tensors by `TensorPtr` (`shared_ptr<Tensor>`) rather than by value in essentially every call site, so forbidding implicit copies costs nothing today; an explicit `.clone()` (real `cudaMemcpy` device-to-device) can be added later if a genuine deep-copy need arises (e.g. M10 batching).

All CUDA-facing code in `Tensor` is gated behind `#ifdef NNFRAME_WITH_CUDA` in `tensor.cpp` only — never in `tensor.h` — so a CPU-only build (the author's laptop) never needs `<cuda_runtime.h>` present to compile `Tensor` at all, matching the existing `NNFRAME_WITH_CUDA` CMake option from M9.

Three device-related failure conditions — calling an op with no CUDA implementation on a GPU-resident tensor, calling `matmul` on two tensors residing on different devices, and calling `.to(CUDA)` in a build with no CUDA support compiled in — all throw a real exception (`std::runtime_error`) rather than following this codebase's existing `assert()`-based convention (used throughout `tensor.cpp`, `attention.cpp`, `KVCache.cpp`, `sampler.cpp` for invariant checks like bounds/shape mismatches). This is a deliberate, scoped break from convention: existing `assert()`s guard programmer bugs within a single device that testing should eliminate before release, and `assert()` is compiled out entirely under `NDEBUG`. Device errors are different — a CPU-only machine calling `.to(CUDA)` is an expected, valid runtime scenario for anyone who clones this repo without a GPU, not a bug to catch only in debug builds; silently no-op'ing or vanishing under `NDEBUG` would leave a tensor claiming a device it isn't actually on, with no signal at all. All other correctness checks in this milestone (shape/index validity, etc.) continue using `assert()` as before — only these three device-boundary conditions use exceptions.
